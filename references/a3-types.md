# A3 报告类型参考

A3 适用于任何行业：IT/软件、服务交付、售后运维、医疗、运营商、项目管理、制造等。所有示例和提问不预设行业。

## 一、问题解决型（标准7分区模板）

### 分区结构

| # | 分区 | 栏位 | 内容要求 |
|---|---|---|---|
| 1 | 背景 / 目的 | left | 为什么要做这件事：问题带来的业务影响（口碑/成本/交付/满意度），加一段"反思"说明为何值得深挖 |
| 2 | 现状 | left | 数据、事实、图表：量化问题的规模、频次、耗时、成本；与基线/其他类别对比突出差距 |
| 3 | 目标 / 课题 | left | 用 **OKR 结构**：1个O（定性方向）+ 2-4个KR（指标：当前值→目标值，期限）。KR须满足三要素：①有依据（基于现状数据）②可度量量化 ③有价值（写明"目标价值"）。KR 即后续跟踪的监控指标 |
| 4 | 根因分析 | left | 表象 → 5WHY → 根本原因。用5Why表格：问题现象 \| Why1 \| Why2 \| ... \| 根因 \| 改善举措。判定标准：**消除该原因即可根治、防止再发**。Why链须由用户逐层确认（见 a3-coaching.md 5Why追问协议） |
| 5 | 解决方案（对策） | right | 多个方案比选、分析利弊、简洁明了、有可行性。对策必须与根因一一对应，且是**直接解决问题症状的具体手段，不是方向或理念** |
| 6 | 执行计划 | right | 表格：行动 / 交付物 / 责任人 / 完成时间 / 对应根因或KR。每行须通过 **SMART 校验**（见下） |
| 7 | 后续行动计划跟踪 | right | 效果确认（用与现状相同的指标对比）+ 持续改善：未达标则分析偏差根因继续优化 + 标准化沉淀与横展 |

### 5Why 表格格式（用于第4区）

| 问题现象 | Why1 | Why2 | Why3 | Why4 | Why5 | 改善举措 |
|---|---|---|---|---|---|---|
| 现象+量化占比 | ... | ... | ... | （追到可行动的根因即停） | | 对应的具体对策 |

### 目标区 OKR 写法（结构示意，不预设行业）

- **O**：一句话定性方向，描述"问题解决后的理想状态"
- **KR1**：核心指标A 当前值 → 目标值，期限（有依据：来自现状数据；价值：写明对业务的意义）
- **KR2**：核心指标B 当前值 → 目标值，期限
- KR 数量 2-4 个；每个 KR 必须有当前值、目标值、期限；期末用同口径复测

### 执行计划 SMART 校验（每行必过）

| 维度 | 检查问题 | 不合格示例 → 合格改法 |
|---|---|---|
| S 具体 | 在哪个节点做什么、输出什么？ | "加强培训" → "第X周对[对象范围]逐一[具体动作]，输出[具体交付物]" |
| M 可衡量 | 完成标准/验收物是什么？ | "推动优化" → "[交付物]完成发布，达到[量化验收标准]" |
| A 可达成 | 责任人有资源和权限吗？超出则标注需要的支持 | — |
| R 相关 | 对应哪条根因或哪个KR？（表中标注编号） | — |
| T 有期限 | 明确完成日期（非"尽快""持续"） | "持续跟进" → "每周五检查，X月X日前完成N轮" |

任一维度不满足时，先向用户追问补齐，不要直接写入报告。

### 现状分析方法（引导用户使用）

- **进现场验证**：调研流程上所有相关角色（不只一方），验证声音真实性；追踪一个具体案例的完整过程还原
- **工序拆解**：把流程拆成工序，分析各环节耗时，区分有效/无效投入
- **对标最优**：找做得好的人/团队/案例，问"为什么他们能做好"（正向5Why）
- **数据对比**：与基线、与其他类别、与友商对比，暴露差距

### 必填信息清单（缺失则提问）

- 问题的具体表现、发生场景和影响（口碑/成本/效率/满意度）
- 至少一个量化指标的当前值
- 期望达成的目标值和期限
- 问题涉及的流程/产品/团队范围

## 二、提案型

### 分区结构

| # | 分区 | 栏位 | 内容要求 |
|---|---|---|---|
| 1 | 背景与目的 | left | 为什么现在提出此提案，与组织目标的关联 |
| 2 | 现状与差距 | left | 现状数据、痛点、与理想状态的差距 |
| 3 | 提案内容 | left | 方案描述：做什么、怎么做、涉及范围 |
| 4 | 方案比选 | left | 至少2个备选方案的对比（成本/效果/风险/周期）。可用评估矩阵邀请相关方共同评估，说明推荐理由 |
| 5 | 预期效果与收益 | right | 量化收益（ROI、节省工时、质量提升）与定性收益 |
| 6 | 资源需求与成本 | right | 预算、人力、设备、时间投入 |
| 7 | 实施计划 | right | 里程碑：阶段 / 交付物 / 责任人 / 时间 / 审核人 |
| 8 | 风险与应对 | right | 主要风险、发生概率、缓解措施；预先讨论"什么事情可能出错" |

### 必填信息清单

- 提案要解决的核心痛点
- 方案的基本内容（至少一个；鼓励补充备选方案）
- 大致的资源/预算规模
- 期望的决策点（批准什么）

## 三、状态汇报型

### 分区结构

| # | 分区 | 栏位 | 内容要求 |
|---|---|---|---|
| 1 | 项目背景与目标 | left | 项目目的、原定目标（量化） |
| 2 | 总体状态 | left | 红/黄/绿灯 + 一句话结论；进度/成本/质量三维状态 |
| 3 | 已完成工作 | left | 关键里程碑达成情况，与计划对比 |
| 4 | 关键指标进展 | left | 指标当前值 vs 目标值 vs 基线，趋势。**同时分析为什么变好、为什么变坏** |
| 5 | 问题与风险 | right | 当前障碍、需要的支持、升级事项 |
| 6 | 下阶段计划 | right | 未来周期重点工作 / 责任人 / 时间 |
| 7 | 需要的决策/支持 | right | 明确向汇报对象提出的请求 |

### 必填信息清单

- 项目名称和原定目标
- 当前进展（完成了什么）
- 汇报周期（周报/月报/阶段报告）
- 是否有需要上级决策的事项

## 质量检查清单（交付前逐项核对）

来自丰田A3工具包的评价标准与常见误区：

- [ ] 内容按问题解决流程展开，各步骤说明方法贴切
- [ ] 使用数据和图表体现，清晰易懂；重点处有明确标注（加粗/醒目颜色）
- [ ] 标题区完整：标题、类型、实践人（作者）、教练（如有）、日期、版本
- [ ] **问题与对策分开**：问题是"为什么会发生X"，不是"该如何解决X"
- [ ] **问题陈述是量化差距**：只写"标准/期望 vs 现状"，不夹带原因（"因为…"）和对策（"需要…"）
- [ ] **叙事连贯**：全篇像一个故事，每区回答上一区引出的疑问，读者5分钟能顺读全篇
- [ ] **没有把线索当根因**：等待、延误、返工等是现象/线索，要继续追问为什么
- [ ] **5Why链由用户逐层确认**：不是AI代填；已做"消除根因后现象是否还会发生"的反向验证
- [ ] 目标为 OKR 结构：1个O + 2-4个KR；每个KR有当前值→目标值+期限，写明目标价值
- [ ] 根因判定：消除该原因即可根治、防止问题再发
- [ ] 对策具体可落地（执行方知道在哪个节点做什么动作、输出什么），不是方向、理念、大而全的建议
- [ ] 每条对策对应一条根因；来源于现场而非拍脑袋
- [ ] 执行计划每行通过 SMART 校验：行动/交付物/责任人/完成时间/对应根因或KR，无"尽快""持续"类模糊期限
- [ ] 有后续跟踪机制：未达标时的偏差分析和持续改善安排
- [ ] 无臆造数据：用户未提供的数字标注为 `[待确认]`
- [ ] 单区内容不超过8行要点（一页纸约束）
